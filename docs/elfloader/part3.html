Findings from my first review that testing withdrew

They are listed so the record is straight. The polled receive calls do work after open() when interrupts are off. rx_clear_errors() does clear an overrun under simavr (S7 in 8.1); on a real chip those flags are read-only and clear when the data register is read, so the call is harmless there. The transmit path through the data-register-empty interrupt is sound: 18 bytes went out in 19 handler calls. The 57600 special case is the deliberate Arduino-compatible behaviour. The read-modify-write on the control register can at worst cause one extra interrupt that switches itself off.

8Simulator findings: simavr and protosim

Running the prototype and the probes turned up behaviour in both simulators that matters to anyone testing firmware with them. This section lists all of it: where simavr differs from a real chip, defects in protosim, and what protosim would need to test this loader without a separate harness. The versions are protosim 6fadc6f and simavr a6fc4cc, the commit protosim pins. The tables describe those versions. Since then protosim f4d382e records reset causes and fixes B2, B6, B9 and B13, and 21fd8b2 keeps the last flash byte that simavr's loader drops (S1): without it a kernel inside protosim does not find the service table, whose last letter is that byte. simavr is unchanged. Recorded probe output is in prototype/results-simulators.txt.

What this means for a bootloader tested in simulation

S2 to S5 are the ones that matter most here. A loader that forgets to erase before writing, forgets to re-enable the read-while-write section, does not wait for an operation to finish, or runs outside the boot section passes every test in simavr and fails on a chip. The prototype does all four correctly, but the simulated results in section 9 are not what shows that. They establish parsing, protocol and addressing. Flash discipline, timing and power loss need hardware. S12 and S13 touch one option: the signature check cannot run on the simulated ATmega2560 at all, and on the ATmega1284P it runs only because the bootloader clears RAMPZ before the read, which a chip does not need.

8.3protosim: additions for testing this loader proposed

  • Binary input. --uart0-in-file, or better an XMODEM sender beside the STK500 one, with a switch for which of the two runs with --bootloader, and one for neither.
  • Flash comparison. --expect-flash <file.elf>: at exit, compare flash with simavr's own load of that file. This is the oracle test of section 9 as a one-line check for CI, and it needs B1 fixed to be of use.
  • Reset into the loader, with a cause. Done in f4d382e: --reset-vector, --reset-cause, --reset-at <ms>[:cause], and on Linux and macOS SIGUSR1 for the reset pin and SIGUSR2 for a power cycle of a running simulation. P1 to P5 in 9.1 use it.
  • A strict flash mode. An option that reports SPM outside the boot section, a page write with no erase before it, and reads of the application section while it is busy. That would turn S2 to S4 from blind spots into test failures. It could live in simavr or as a check in protosim.

9.2Run-time module loading in simulation

Here the bootloader only sits in flash. The test kernel of 6.8 runs on the ATmega328P (M1 to M9) and on the ATmega2560 (M10 to M12): protoduino's scheduler with the serial device process, a kernel process, a heartbeat process and the loader process. 9.5Not verified

  • Anything on hardware, including fuse and lock-bit settings and real programming times.
  • Loss of power during an update. The transaction argument in 4.4 is by construction.
  • The bootloader on an ATtiny: it has never executed. Only its run-through mechanism was checked, on the ATmega328P (T13). The shell runs on the ATtiny85 (S5); nothing is loaded there.
  • Flash discipline. simavr accepts a missing erase, a missing read-while-write re-enable and SPM from the application section (8.1), so the simulated results cannot show that the loader gets these right.
  • The device-signature check on the ATmega2560: simavr's core for that part has no signature row (S12). The check ran on the ATmega328P and the ATmega1284P (T8, T9, T15, T16).
  • The Optiboot flash driver above 128 KB of flash. The build stops with an error there.
  • The watchdog on a chip: the 16 ms between resets that simavr stretches (S14), and a part whose fuses keep the watchdog on, which simavr does not model. Reset through the pin and brown-out are not recorded by simavr (S11): the harness writes the cause into MCUSR at each reset it makes, as protosim does.
  • How long a real page write holds the system up during a load, and what that does to micros().
  • Module loading on the ATmega1284P.
  • The host tools on a real serial port: talk.mjs was only used on protosim's pseudo terminal.
  • Optiboot on a real board, and Optiboot versions other than the 8.3 image that was used.

9.6Test plan from here

  • Host unit tests in CI for the core, with the files above as fixtures, and a fuzzer on elf_stream_write(). The stream is small, pure C and takes untrusted input, which is the ideal fuzzing target.
  • protosim end to end per supported part. tools/test_systems.sh is the start: S1 to S4 run in protosim as it is. The oracle comparison of T1 to T29 and M1 to M12 still needs the additions of 8.3 and B1 fixed.
  • Hardware: an Uno and a Mega 2560, with an ISP programmer at hand for fuses. A relay on the supply to cut power at random points of an update, hundreds of times, checking that the board always answers afterwards.

Risks

  • Size. The protothread form costs 374 bytes, of which assembly and numbered continuation points recovered 76. On the ATmega328P the 2 KB section has 28 bytes left. The parts above 64 KB use the 4 KB section, where 1,146 bytes are free.
  • The far call. Four instructions that rely on which registers avr-gcc passes arguments in. A compiler that changes that breaks the call without a message; T20, T21, M10 and M11 would show it.
  • Page writes still stop the system. Cooperative means between pages. Each page holds everything for 7 to 9 ms on a chip, and no AVR design can avoid that.
  • The scheduler under load. Until finding 14 is fixed, a process that waits for an event waits out every block of a transfer.
  • ATtiny recovery. Without hardware protection for the bootloader's pages, a faulty application can destroy it. The claim for these parts is deliberately weaker.
  • Exact binding. Convenient while developing, awkward for distributing modules. The table scheme is the answer and costs flash.
  • Optiboot is a moving target. The flash driver relies on where Optiboot puts do_spm and on its size. Both are checked at run time, but only version 8.3 was tried.
  • Old compiler. All sizes are from avr-gcc 7.3.0. A newer one may be better or worse, and it turns finding 10 into a link error.
  • Unload. Queued events hold plain process pointers, and a slot's RAM block is reused: an event still in the queue can reach the next module in that slot. The shell's del is built without a guard against that: a new module is only accepted once the process of the old one has ended, which leaves the window of an event posted before and delivered after. Purging the queue for a process that ends, or handles with a generation, would close it.

Open questions

Settled on 12 November 2026: the ATmega2560 and ATmega1284P take a 4 KB boot section, and the bootloader is built with every option there; no blocking build is kept for 2 KB. On the ATmega328P the 2 KB section keeps the exported load thread and gains the immediate restart after a watchdog reset; segment merging made room for it, and a fourth segment entry does its work. The bootloader waits for a sender only after a reset through the pin; protosim was given reset causes so that this can be run in simulation.

  • Which small part is meant by “ATtiny8”? The answer decides whether the small-frame transport is needed early.
  • Should updates be authenticated, and if so with what? A keyed hash costs several hundred bytes.
  • Which binding scheme is the default for modules: exact or table?
  • Should module slots be allowed above 64 KB on the large parts? Today that is a build error; lifting it needs far reads in the scheduler.
  • Where should the bootloader's build live, given that it cannot be under src/?

BReproducing the measurements

The code is in the library (6.1), the test bench in docs/elfloader/prototype/. It needs gcc-avr, avr-libc, libelf-dev, Node.js 22 and protosim built with its simavr submodule. The Optiboot image is not included: copy optiboot_atmega328.hex from the Optiboot repository into fixtures/ for M2, M4 and M8.

./make_fixtures.sh                       # test files, and the test kernels with their modules

# the stream on the host, against a file built with avr-gcc
gcc -std=gnu11 -O2 -DELF_CONF_EEPROM=1 -DELF_CONF_SIGNATURE=1 -DELF_CONF_MAX_SEGMENTS=6 \
    -I../../../src -o host_test host_test.c ../../../src/sys/elf.c
./host_test fixtures/app-atmega328p.elf 5 out.bin

# the harness that runs the bootloader inside simavr
S=../../../../protosim/libraries/simavr/simavr
gcc -O2 -o sim_harness sim_harness.c -I$S/sim -I$S/sim/avr \
    $S/obj-x86_64-linux-gnu/libsimavr.a -lelf -lm -lpthread

./run_tests.sh                           # T1 to T29
./run_modules.sh                         # M1 to M12
./run_protosim.sh                        # P1 to P5, in protosim itself
./fit.sh atmega2560                      # fill the standard boot section of a part

./build.sh m2560 atmega2560 default -DBOOT_CONF_LOAD_SERVICE=1
