Findings from my first review that testing withdrew

They are listed so the record is straight. The polled receive calls do work after open() when interrupts are off. rx_clear_errors() does clear an overrun under simavr (S7 in 8.1); on a real chip those flags are read-only and clear when the data register is read, so the call is harmless there. The transmit path through the data-register-empty interrupt is sound: 18 bytes went out in 19 handler calls. The 57600 special case is the deliberate Arduino-compatible behaviour. The read-modify-write on the control register can at worst cause one extra interrupt that switches itself off.

What this means for a bootloader tested in simulation

S2 to S5 are the ones that matter here. A loader that forgets to erase before writing, forgets to re-enable the read-while-write section, does not wait for an operation to finish, or runs outside the boot section passes every test in simavr and fails on a chip. The prototype does all four correctly, but the simulated results in section 9 are not what shows that. They establish parsing, protocol and addressing. Flash discipline, timing and power loss need hardware.

8.3protosim: additions for testing this loader proposed

  • Binary input. --uart0-in-file, or better an XMODEM sender beside the STK500 one, with a switch for which of the two runs with --bootloader, and one for neither.
  • Flash comparison. --expect-flash <file.elf>: at exit, compare flash with simavr's own load of that file. This is the oracle test of section 9 as a one-line check for CI, and it needs B1 fixed to be of use.
  • Reset into the loader. B9, so that an application's request for an update can be tested.
  • A strict flash mode. An option that reports SPM outside the boot section, a page write with no erase before it, and reads of the application section while it is busy. That would turn S2 to S4 from blind spots into test failures. It could live in simavr or as a check in protosim.

The same stream, compiled natively, was fed real files in chunks of random size and its output compared with avr-objcopy.

9.5Not verified

  • Anything on hardware, including fuse and lock-bit settings and real programming times.
  • Loss of power during an update. The transaction argument in 4.4 is by construction.
  • The ATtiny path: it has never executed. Only its run-through mechanism was checked, on the ATmega328P (T13).
  • Flash discipline. simavr accepts a missing erase, a missing read-while-write re-enable and SPM from the application section (8.1), so the simulated results cannot show that the loader gets these right.
  • The image CRC check at start-up, the information reply, and the service table on parts above 128 KB.
  • How long a real page write holds the system up during a load, and what that does to micros().
  • Module loading on any part but the ATmega328P, and with the Arduino core in place of the stand-in for it.
  • Optiboot on a real board, and Optiboot versions other than the 8.3 image that was used.

9.6Test plan from here

  • Host unit tests in CI for the core, with the files above as fixtures, and a fuzzer on elf_stream_write(). The stream is small, pure C and takes untrusted input, which is the ideal fuzzing target.
  • protosim end to end per supported part, once the additions of 8.3 exist and B1 is fixed, with the oracle comparison as the pass criterion. The module scenarios M1 to M9 belong in the same suite.
  • Hardware: an Uno and a Mega 2560, with an ISP programmer at hand for fuses. A relay on the supply to cut power at random points of an update, hundreds of times, checking that the board always answers afterwards.

Risks

  • Size. The protothread form costs 374 bytes. On parts above 64 KB the bootloader needs the 4 KB section; on the ATmega328P the 2 KB section is full to within 6 bytes.
  • Page writes still stop the system. Cooperative means between pages. Each page holds everything for 7 to 9 ms on a chip, and no AVR design can avoid that.
  • The scheduler under load. Until finding 14 is fixed, a process that waits for an event waits out every block of a transfer.
  • ATtiny recovery. Without hardware protection for the bootloader's pages, a faulty application can destroy it. The claim for these parts is deliberately weaker.
  • Exact binding. Convenient while developing, awkward for distributing modules. The table scheme is the answer and costs flash.
  • Optiboot is a moving target. The flash driver relies on where Optiboot puts do_spm and on its size. Both are checked at run time, but only version 8.3 was tried.
  • Old compiler. All sizes are from avr-gcc 7.3.0. A newer one may be better or worse, and it turns finding 10 into a link error.
  • Unload. Queued events hold plain process pointers, and a slot's RAM block is reused: an event still in the queue can reach the next module in that slot. Removal needs the queue purged or generation-checked handles first.

Open questions

  • Which small part is meant by “ATtiny8”? The answer decides whether the small-frame transport is needed early.
  • Should updates be authenticated, and if so with what? A keyed hash costs several hundred bytes.
  • Which binding scheme is the default for modules: exact or table?
  • Is the default order for filling the boot section the right one? On the ATmega328P it trades the merging of segments for the load thread.
  • Is a 4 KB boot section acceptable on the ATmega2560 and ATmega1284P, or should a blocking build be kept for the 2 KB section there?
  • Should the bootloader wait after every reset, or only on request? It changes start-up time by seconds.
  • Where should the bootloader's build live, given that it cannot be under src/?

For the ATmega328P test program avr-gcc wrote six loadable segments: code at load address 0; initial .data at run address 0x800100 but load address 0x136, directly after the code; .bss with no file bytes; EEPROM at 0x810000; fuses at 0x820000; signature at 0x840000. measured

BReproducing the measurements

The code is in docs/elfloader/overlay/, the test bench in docs/elfloader/prototype/. It needs gcc-avr, avr-libc, libelf-dev and protosim built with its simavr submodule. The Optiboot image is not included: copy optiboot_atmega328.hex from the Optiboot repository into fixtures/ for M2, M4 and M8.

./make_fixtures.sh                       # test files, and the test kernels with their modules

# the stream on the host, against a file built with avr-gcc
gcc -std=gnu11 -O2 -DELF_CONF_EEPROM=1 -DELF_CONF_SIGNATURE=1 -DELF_CONF_MAX_SEGMENTS=6 \
    -I../overlay/src -I../../../src -o host_test host_test.c ../overlay/src/sys/elf.c
./host_test fixtures/app-atmega328p.elf 5 out.bin

# the harness that runs the bootloader inside simavr
S=../../../../protosim/libraries/simavr/simavr
gcc -O2 -o sim_harness sim_harness.c -I$S/sim -I$S/sim/avr \
    $S/obj-x86_64-linux-gnu/libsimavr.a -lelf -lm -lpthread

./run_tests.sh                           # T1 to T13
./run_modules.sh                         # M1 to M9
./fit.sh atmega328p 2048                 # fill one boot section
./sizes.sh                               # the tables of 6.8 to 6.10
probes/run_probes.sh                     # findings 10 to 22 of section 7
./build.sh m2560 atmega2560 0x3F000 -DBOOT_CONF_LOAD_SERVICE=1

Recorded outputs are in results-sizes.txt, results-fit.txt, results-tests.txt, results-modules.txt, results-library.txt and results-simulators.txt. Findings 1 to 9 of section 7 come from the other programs in probes/, built against protoduino's own sources and run with protosim --uart0-in … --uart0-out …; the simulator findings of section 8 from simprobes/ and sim_harness --fallthrough.
