What is real in this document

  • The loader was written and run for this document. Every figure marked measured comes from it: avr-gcc 7.3.0, and simavr at the commit that protosim pins.
  • Module loading runs on protoduino's unmodified scheduler, serial device process and pipes, in a sketch built without the Arduino core, on the ATmega328P.
  • Nothing has run on hardware. Power loss was not simulated. simavr programs a page in no time, so timings leave out the 7 to 9 ms a real page costs (8.1). Relocation (4.8) is a design; the ATtiny build compiles and has not executed.
  • No protoduino, protosim or simavr source file was changed; the fixes in sections 7 and 8 are proposals. The code is in docs/elfloader/overlay/, laid out as it would land in the library; the test bench is in docs/elfloader/prototype/.

1Summary

The loader takes the file the linker writes, the .elf, and treats it as a stream. The first 52 bytes say what the file is. The next 32 bytes per program header say which bytes belong where. Everything after that is delivered to flash in the order it arrives. The stream never seeks backwards and never allocates, and all of its state fits in one 84-byte structure. When the last loadable byte has been delivered it is done; the symbol tables and debug information that make up most of the file never have to be sent.

Around the stream sits one Protothreads v2 thread, elf_load_thread(). It receives the file with XMODEM-CRC, feeds the stream and programs the pages. It does no input or output of its own and reads no clock: bytes pass through a small mailbox in its workspace, and it returns to its caller between any two of them. That one thread is used in three places, chosen at compile time:

  • As the bootloader. At reset nothing else exists, so a loop of a dozen lines schedules the thread from a polled uart0. Any terminal program can send the unmodified .elf. An image record written last decides whether the application may start.
  • As a boot ROM for the running system. The boot section exports the address of the thread. A protoduino process schedules it with the bytes its pipe delivers, and every other process keeps its turn while a module arrives. The kernel pays for a process, not for a loader.
  • Inside the kernel. Where the bootloader is Optiboot, or a protoduino bootloader built without the export, the kernel links its own copy of the thread and has pages programmed through whatever the bootloader offers.

Loading is therefore cooperative everywhere, and it is not a feature that a larger boot section switches on. The fuses decide only where the thread lives: in the boot section when it fits, in the kernel when it does not (4.6). The build fills the section that the fuses reserve with as many options as fit, in a set order of priority (6.9).

Modules fit protoduino in particular. A module is a process type: the same record PROCESS_DEFINE emits for a built-in process, linked into a flash slot and started with process_new(). Protothread processes keep their state in a struct the kernel hands them, so a module needs no static RAM, and the hardest part of dynamic loading on an AVR, relocating data addresses, does not arise.

The size is the weak point, and it should be stated plainly. Optiboot fits in under 512 bytes; this bootloader is 2,014 bytes, in plain C with an old compiler. Writing it as a protothread cost 374 bytes against the blocking version of the previous draft (1,640 bytes), and on parts with more than 64 KB of flash that pushed it out of the 2 KB boot section into the 4 KB one. What the bytes buy is in 4.6; where they go is in 6.10.

Building on the library also turned up eleven more findings in protoduino itself, among them that process_run() lets polls starve events and that a process which ends is never cleaned up unless another event happens to reach it. Section 7 lists them with measurements and patches.

2Goals, non-goals and target parts

Goals

  • Accept the linker's own output. No hex file, no binary image and no packaging step for firmware.
  • One core, used in parts. From a bootloader to a loader inside the kernel, with features that cost nothing when switched off.
  • Fill the boot section. Whatever block the fuses reserve is used for as many features as fit.
  • Refuse before erasing. The wrong file must be rejected while the installed image is still intact.
  • Always recoverable. On parts with a hardware boot section, no failed update may leave a device that cannot be reached over the same serial line.
  • Modules are processes, loadable at run time. Wherever the part can carry it and unless it is configured out. Three levels: none, modules already in flash, run-time loading.
  • Loading never stops the system. The loader is a protothread among protothreads, and it reads like the rest of protoduino.
  • Not tied to our bootloader. A protoduino kernel can load modules on top of Optiboot as well.

Non-goals

  • Linking on the device. Relocatable .o files, symbol tables and name lookups stay on the host.
  • Authenticated updates in the first version. Integrity is checked; origin is not. The reserved byte of the module descriptor is where a signature would be announced (6.8).
  • C++ runtime features in modules. No exceptions, RTTI or static constructors.
  • Parts without room for a page buffer. The ATtiny4/5/9/10 have 32 bytes of RAM.
  • UPDI-era parts in this document. tinyAVR 0/1/2 and AVR Dx program flash through NVMCTRL. They need another flash back-end, which the layering allows but which is not designed here.

3What earlier loaders got wrong

Five existing designs were examined, four of them in source. Each got something right that this design keeps, and each left something that it changes.

LoaderWhat it does, and where it falls shortWhat this design does instead
Contiki ELF loader
2005 to 2017 read		 Loads relocatable .o files and links them on the device. It makes 14 seek-and-read calls, recognises ten sections by comparing name strings, and resolves every import with strcmp against a table of names compiled into the kernel. So the whole file must already sit in a seekable store, and the kernel carries its symbol names in flash. It checks the first seven identification bytes and never the machine type. Contiki later added a pre-linked format (CLE), and Contiki-NG deleted the loader in 2017, 4,203 lines in one commit. No linking on the device. The file is consumed as it arrives. Machine and core family are checked from the header. What Contiki got right is kept: a module is a set of processes, and architecture code is separate from the core.
Optiboot with avrdude Under 512 bytes, which is the bar for size. But the device receives anonymous pages: it has no idea what the image is, keeps no record of whether it is complete, and starts whatever is there after a timeout. The host has to turn the ELF into a hex file and speak a programmer protocol. Version 8 added do_spm() so an application can write flash. The device reads the ELF header itself and keeps an image record. The do_spm() idea is kept and widened: the boot section lends out its whole load thread (6.7). Optiboot also stays a supported choice: a protoduino kernel loads modules on top of it (6.8).
urboot, micronucleus
parts without a boot section		 They patch the application's reset vector so that reset reaches the loader, and rely on erased flash running through to it. The known hazard, in urboot's own words: if the first page is erased but not rewritten, the part is bricked until it meets an ISP programmer. Erase from the top down with page 0 last, and give the loader a landing pad. There is then no instant at which a reset fails to reach the loader (6.6). proposed The run-through and the landing pad were checked in simulation (T13).
simple-avr-bootloader
m3y54m; a tutorial by its own description read		 Sends a raw binary with a 16-bit length. Frames carry an 8-bit additive checksum and no sequence number, and the uploader retries on timeout, so a lost acknowledgement makes the same chunk land twice. The update flag sits 8 bytes below the top of RAM, where the stack starts. The loader runs its serial port from interrupts and has no check that the application is whole. XMODEM-CRC: 16-bit CRC and block numbers, so a repeat is acknowledged and dropped. A polled serial port with no vectors. An image record. Its good idea is kept: the application asks for an update, then resets.
Host ELF libraries
libelf, ELFIO and others		 They assume random access or the whole file in memory, and they allocate. None is built to be fed. Used only as oracles in tests.
Zephyr LLEXT
a current reference		 Still links on the device, but can replace symbol-name strings with hashes to save space. That is the right direction, and still far too much code for an 8-bit part. One step further: no symbol table on the device at all. A module is linked on the host against one firmware build and carries that build's identity (6.8).
protoduino docs/loader.md read Describes modules that are stored in RAM and run from there, which an AVR cannot do: code executes only from flash. It compiles with -fpic, which avr-gcc reports as unsupported. It refers to functions that are not in src/. Its file header has no magic number, version or checksum. Superseded by this document.

An earlier note of mine questioned the order in which simple-avr-bootloader fills, erases and writes a page. That was wrong: the datasheet allows the page buffer to be filled either before or after the erase.

4The ideas the design rests on

4.1The ELF file is the wire format

An executable from avr-gcc is laid out in the order a loader needs it. The ELF header comes first, the program headers follow at offset 52, the loadable bytes come next, and everything a loader has no use for comes last. A reader that only moves forward can therefore do the whole job, and can stop early.

The consequence for the user is that no tool has to be installed to flash a board. With XMODEM as the transport (6.4), a terminal program that every platform already has can send the file the build produced.

4.2One core, used in parts

The stream is a state machine with no input or output of its own. Bytes are pushed in from whatever carries them; bytes that belong in a memory are handed to a sink. Around it sits one protothread, the code that receives a file and feeds the stream, written so that all of its state is in a workspace the caller owns. That makes the thread usable from three places: the bootloader at reset, the boot section scheduled by the running kernel, and a kernel that links it in.

Which parts end up where depends on two choices: what sits in the boot section, and how much module support the kernel is built with.

4.3Address spaces select the sink

avr-gcc gives every memory of the chip its own range in the ELF address space, so the top byte of a segment's load address says where its bytes belong. The loader routes on that byte. It uses the load address (p_paddr), not the run address: the initial values of .data are stored in flash right after the code, and the program's own start-up copies them to RAM.

Two checks come free with the format. The header's flags name the core family the file was built for (avr:5 for an ATmega328P, avr:6 for an ATmega2560, avr:25 for an ATtiny85), and avr-gcc defines the same number as __AVR_ARCH__ when the loader is compiled. One comparison rejects a file for the wrong family from its first 52 bytes. The signature check is finer, down to the exact device, but it comes late, because avr-gcc places the signature after the flash data (see FR-9).

4.4Refuse before erasing, commit last

An update is a transaction with one commit point. Nothing in flash changes until every program header has been accepted. The installed image is declared invalid before its first byte changes, and becomes valid again only when a small record is written after the last byte. A reset at any moment therefore finds either the old image, or no valid image and a waiting loader, or the new image.

4.5The boot section as a small ROM

On a megaAVR the SPM instruction works only from the boot section, so an application cannot program flash by itself, and a run-time loader in the application cannot exist without help. The boot section therefore exports a table at a fixed place at the very end of flash. Its first entry programs one page from the caller's buffer, as Optiboot's do_spm() does. Its second is the address of the load thread itself: the same code that loaded the firmware at reset, to be scheduled by the running system on a workspace the system owns. The boot section is paid for anyway; this makes it do the kernel's loading too (6.7). measured

4.6One thread, two schedulers

The previous draft exported a blocking session: the kernel called into the boot section and got control back seconds later, when the module was in flash. This draft exports a protothread, and that changes what the kernel can do while a module arrives.

What was measured. A sketch on protoduino's scheduler ran the serial device process, a kernel process, the loader process and a heartbeat process that takes a turn as often as it can. While a 3,184-byte module file arrived in 350 ms, the heartbeat took 18,053 turns. With the blocking session of the previous draft it would have taken none. measured

How long the others wait. The longest wait of the heartbeat was 15.1 ms, the time one XMODEM block spends on the wire. That is not the loader: process_run() serves polls before events, and the serial device polls on every received byte, so an event-driven process waits out the block (7, finding 14). Built against a copy of process.c with that one function changed, the longest wait fell to 2.0 ms, which is the time the thread needs to check a block and push it through the stream. measured On a chip, each page adds 7.4 to 9.0 ms: an AVR cannot execute application code while it erases and programs application flash, and interrupts stay off for that time. No design removes that; XMODEM's stop-and-wait keeps the sender quiet meanwhile.

Is cooperative loading tied to a fuse setting?

No. There is one implementation of the load, the thread, so every build that can load at all loads cooperatively. The size of the boot section decides only where the thread lives:

  • ATmega328P, 2 KB section. The bootloader with the thread exported is 2,042 bytes. The kernel schedules the thread in the boot section and links 1.7 KB for the loader process and module table.
  • ATmega328P, 4 KB section. The same, plus every other option, in 2,358 bytes.
  • ATmega1284P and ATmega2560. The bootloader needs the 4 KB section and then exports the thread too (2,970 and 2,972 bytes with everything).
  • Optiboot, or a section that is too small for the export. The kernel links its own copy of the thread, 3.1 KB in all, and loads just as cooperatively.

The build step of 6.9 makes the choice from the block size. BOOT_CONF_LOAD_SERVICE forces it either way, and LOADER_CONF_THREAD tells the kernel which thread to schedule.

4.7A module is a process type

protoduino already has the right descriptor. process_type_t is a small record in flash holding a name, a thread function, an instance size and a priority, and process_new(type, storage) turns it into a running process in memory the caller supplies. A loadable module is exactly that record plus its code, linked into a flash slot. Its source is an ordinary process, written with PROCESS_DEFINE and PROCESS_THREAD, with one more line: MODULE(name). Loading a module means programming its bytes and calling the function every built-in process type is started with. measured

Protothreads are stackless, and a protoduino process keeps its variables in its instance struct. A module written that way has no .data and no .bss, so there is nothing in RAM to place or relocate: the kernel hands the thread a pointer, and the module works wherever that points. The rule is enforced at link time rather than left to discipline (6.8).

4.8Relocation without a relocator

A module is linked for one slot, which needs no code on the device. To let one file load into any slot, addresses inside the module must be adjusted, and the usual way needs a relocation engine. There is a cheaper way. If slots are aligned to 512 bytes, moving a module changes only the high byte of every byte address and of every word address; low bytes never change and no carry crosses between them. A fix-up then is one position in the stream whose high byte gets a constant added. The host sorts those positions by offset and puts the list ahead of the code, and the loader applies them as the bytes go by, still in one pass. On parts with absolute call instructions, calls from the module into the kernel need no fix-up at all. proposed

4.9The same core on the host, and the simulator as oracle

The stream is plain C with no AVR dependency, so it compiles unchanged for the host. That gives three things: unit tests and fuzzing at desktop speed; a host tool that can say exactly what a device will accept, because it runs the device's code; and, compiled to WebAssembly, the same check inside a Node command-line tool or protosim's web front end. For end-to-end tests, the simulator already contains a trusted ELF reader. Flashing a file through the loader inside simavr and comparing the result with what simavr's own reader produces for the same file tests the loader against an independent implementation. Section 9 reports that comparison.
