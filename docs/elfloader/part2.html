5.3Start-up behaviour

After a reset the bootloader probes for a sender: it waits for about a second of silence, transmits C, and repeats. A transfer may begin at any probe. If none begins within the configured number of probes and the image record is intact, the image is started. If the record is not intact, the bootloader probes for ever. After a refusal the window opens again. In simulation the probes came 0.950 s apart, and with three probes the image started 3.8 s after reset. measured

Which resets open the window is a setting, BOOT_CONF_WINDOW_AFTER: a mask of reset causes. By default only a reset through the pin does, which is what an upload tool and a reset button make, and the rule Optiboot uses. After power-on, a brown-out or a watchdog reset a complete image starts at once: a board is up without the 3.8 s, an image that the watchdog stopped is running again, and no probe goes out on a serial line that belongs to the application. A board without a reset line can add power-on and brown-out to the mask and is then updated by cycling its power; with all four causes the bootloader waits after every reset. An image that jumps to the bootloader is always waited for: that is how a running system asks to be replaced. The three settings and the jump were run in the harness (T23 to T27), and the default inside protosim (P1 to P5). measured

The watchdog. An image that the watchdog resets, because it hung or because that is how it restarts itself, leaves the watchdog running at its shortest period, 16 ms, until software clears the cause and switches it off. A bootloader that ignores this is reset again long before its first probe, over and over, and the board stays dead until power is cycled. The previous draft of this bootloader did ignore it, and in simulation the image never came back (T22). It now deals with the watchdog before anything else and hands the reset cause to the image (6.5); the same image then restarts at once after every watchdog reset (T23). measured

5.5Limits

  • At most 255 program headers; at most ELF_CONF_MAX_SEGMENTS separate loadable segments after adjacent ones are merged. Plain firmware needs one.
  • File offsets and sizes must fit the build's address width: 64 KB on small parts, 16 MB on large ones.
  • Flash segments must arrive in ascending address order, because the page cache only moves forward. avr-gcc output does. A read-modify-write option would lift this. proposed
  • The workspace of the load thread is 377 bytes on parts with 128-byte pages and 525 on parts with 256-byte pages: an XMODEM block, one flash page, the stream and 26 bytes of bookkeeping.
  • A module is linked for one slot, and modules, their process types and their strings must lie in the first 64 KB of flash: process_new() reads a process type through a near pointer.

6Technical design

6.1Where the pieces live

The loader is part of the library. It follows the conventions of the files around it: a // file: line on top, a block comment that states what the unit is independent of, settings in a *.conf.h with #ifndef defaults, CC_* macros, a selector header in sys/ for platform code in cpu/avr/, ptstate_t results and ERR_* codes.

Two kinds of code, because an Arduino library is compiled apart from the sketch that uses it. The stream, the load thread and the flash driver are library sources: they are compiled with the defaults of their *.conf.h, and a sketch that does not use them pays nothing, because the linker leaves them out. Module slots and the loader process depend on settings only the sketch knows (how many slots, where, which load thread), so they are headers that the sketch includes after its settings, like the process types of src/mod/. A sketch in the Arduino IDE can therefore load modules without a change to the library.

The Arduino build compiles every source file under src/. The bootloader has its own entry code and no C runtime, so it stays outside that tree. It is one translation unit: boot.c includes sys/elf.c, sys/elf/load.c, cpu/avr/flash.c and the library's own cpu/avr/uart0.c, so that the compiler sees the stream, its sink and the drivers together.

6.2The stream

/* Start a stream. Flash bytes outside [lo, hi) are refused before anything reaches the sink. */
void      elf_stream_init(elf_stream_t *s, elf_addr_t lo, elf_addr_t hi);

/* Push the next len bytes of the file. Returns PT_WAITING to be fed more, PT_ENDED when every
   loadable byte has been delivered, or an error code. */
ptstate_t elf_stream_write(elf_stream_t *s, const uint8_t *src, uint8_t len);

/* The sink: store one byte. Returns ERR_SUCCESS to continue, or the error the stream ends with. */
uint8_t   elf_stream_sink(elf_stream_t *s, uint8_t space, elf_addr_t addr, uint8_t byte);

The stream answers in the vocabulary of the framework: PT_WAITING while it wants more, PT_ENDED when it is done, and above that an error from errors.h. A protothread can pass its result straight on.

Header rules. Seventeen bytes of the ELF header must each have one exact value: the magic, the class, the byte order, the file type, the machine, the position and size of the program headers. They are checked by a loop over a 34-byte table of offset and value pairs, which is smaller than seventeen comparisons and easy to extend.

What is remembered. The data of a segment arrives after all the headers, so each loadable segment is remembered as three numbers: the count of file bytes to skip before it, the address of its next byte, and the bytes still to deliver. Storing the gap and not the absolute offset removes the need to count file position at all. A segment that continues the previous one, both in the file and in memory, can be merged into it (ELF_CONF_COALESCE); .text and .data always do, so plain firmware is then one remembered segment. Merging does nothing else: it saves an entry of six bytes, nine on parts above 64 KB, and costs 62 bytes of code. A kernel, where RAM is short, merges. The bootloader does the opposite: it leaves merging out and keeps four entries, which hold code, initial data and two further blocks, the same files as three entries with merging. A file with four flash segments loaded; one with five was refused at its fifth header (T28, T29). measured

Layout. The scratch area for header bytes is the first member of elf_stream_t, so that header bytes and the hot control fields are all within the 63-byte reach of one pointer. On AVR that matters more than it looks: see 6.10.

What building it taught

  • A refused file must not cost the installed image. The first version erased the record when the first block arrived. A wrong file then left a working board without a valid image. Invalidation now happens with the first page write, after the headers are accepted. Test T7 guards it.
  • Above 64 KB, tables in flash need the far read. In the ATmega2560's boot section the rule table sits beyond the reach of LPM. The loader refused every file until the table was read through ELPM.
  • Code in the boot section owns no RAM once the system runs. The thread and the page service work on the caller's workspace and buffer alone.
  • A table of relative jumps does not span an 8 KB boot section. The service table holds addresses. Without an explicit keep, the linker's garbage collection also dropped the table and its services without a word.
  • The event queue belongs to everybody. The first loader process posted itself an event on every turn. Under load the queue of the scheduler filled, and the event that should have told the kernel “the module runs” was dropped without a trace. The loader now keeps at most one event of its own in the queue.
  • PT_RAISE() takes effect on the next schedule. A thread that is only scheduled when there is news for it would send its refusal a second late, and a process that raises waits for an event that may never come. The load thread raises and runs its handler within one call; the loader process asks for a turn before it raises (7, finding 21).
  • Byte counts move in both directions. A check that looked cheaper where a page is committed came out 16 bytes larger than the same check per byte. Every change was measured, and three were taken back.

6.4The load thread

The thread speaks XMODEM with 16-bit CRC. It is decades old and exactly right for this job.

PropertyWhy it matters here
Built into terminal programs on every platformThe unmodified .elf can be sent with no tool of ours installed.
The receiver sets the pace: one block, one acknowledgementThe thread programs pages while it handles a block and acknowledges afterwards. No flow-control lines are needed, and the sender is silent while a page is programmed with interrupts off.
Blocks are numberedA block repeated after a lost acknowledgement is recognised and not applied twice.
CRC-16 per blockThe same CRC routine also protects the image record and the image, so there is one checksum routine in the loader.

A block is SOH, the block number, its complement, 128 data bytes and two CRC bytes. The thread holds a block in its workspace until the CRC has passed, and only then pushes it into the stream, so damaged bytes never reach flash. One extension is used: after cancelling with two CAN bytes the thread sends the reason code. Terminal programs ignore it; the pd tool prints it.

The mailbox. The thread touches no hardware. Whoever schedules it puts each received byte into a one-byte mailbox, tells it when the line has been silent for about a second, and takes up to three reply bytes out. The four calls are named after the serial layer they stand in for:

elf_load_init(&load, lo, hi, ELF_LOAD_MODULE, tries);   /* window, kind of file, probes to send */

if (elf_load_write_available(&load))
  elf_load_write8(&load, byte);                         /* a byte from the sender               */
elf_load_timeout(&load);                                /* or: the line is silent               */

state = elf_load_thread(&load);

while (elf_load_read_available(&load))
  send(elf_load_read8(&load));                          /* its answer, if it has one            */

The thread, as it stands in src/sys/elf/load.c. Judging a frame is a plain function, elf_load_frame(), which answers like the stream does: PT_WAITING to go on, PT_ENDED for a complete file, PT_EXITED when nobody started to send, or an error.

PT_THREAD(elf_load_thread(struct elf_load *self))
{
  struct pt *pt = &self->pt;

  PT_BEGIN(pt);

  self->seq = 1;
  self->end = 0;
  elf_stream_init(&self->stream, self->lo, self->hi);

  do
  {
    // Collect one frame: a block that starts with SOH, or the single byte
    // that is not the start of one, or nothing when the line stays silent.
    for (self->fill = 0; self->fill != ELF_LOAD_BLOCK_SIZE; )
    {
      uint8_t event;

      ELF_LOAD_WAIT_RX(pt, self);     // PT_WAIT_UNTIL(pt, flags & (ELF_LOAD_RX | ELF_LOAD_SILENT))
      // take what the mailbox holds: a byte, or the news that there is none
      event = self->flags & (ELF_LOAD_RX | ELF_LOAD_SILENT);
      self->flags ^= event;
      if (!(event & ELF_LOAD_RX))
        break;
      self->block[self->fill++] = self->rx;
      if (self->block[0] != ELF_LOAD_SOH)
        break;
    }

    // Judge it. The answer for the sender is in the mailbox afterwards.
    self->result = elf_load_frame(self);
    if (self->result >= PT_ERROR)
      ELF_LOAD_RAISE(pt, self, self->result);
    if (self->result == PT_EXITED)
      PT_EXIT(pt); // nobody is sending
  }
  while (self->result != PT_ENDED);

  PT_CATCHANY(pt)
  {
    // Refused: cancel the transfer, tell the sender why, and end with the
    // error that was raised.
    self->tx[2] = ELF_LOAD_CAN;
    self->tx[1] = ELF_LOAD_CAN;
    self->tx[0] = self->result;
    self->txn = 3;
    PT_THROW(pt, self->result);
  }

  PT_END(pt);
}

Two details. All state is in struct elf_load, whose first member is struct pt, as the layout rule of process.h asks; the only local variable, event, does not live across the wait. And ELF_LOAD_RAISE() is PT_RAISE() with one difference: it sets the error with LC_RAISE() and then calls the thread again at once, so the handler runs within the same call. PT_RAISE() itself returns PT_WAITING and lets the handler run on the next schedule, which for this thread would be the next byte or a second of silence.

The scheduler of a system with one thread is the loop in boot/boot.c. It uses the polled calls of the library's own cpu/avr/uart.h:

static CC_NO_INLINE ptstate_t boot_schedule(struct elf_load *self)
{
  uint16_t idle = 0;
  ptstate_t state = PT_WAITING;

  do
  {
    if (uart0_rx_is_ready())
    {
      elf_load_write8(self, uart0_rx_read8());
      idle = 0;
    }
    else
    {
      __asm__ __volatile__ ("wdr");   // for a part whose fuses keep the watchdog running
      _delay_loop_1(BOOT_CONF_IDLE_DELAY);
      // 65,536 idle passes in a row: nobody is sending
      if (++idle != 0)
        continue;
      elf_load_timeout(self);
    }

    state = elf_load_thread(self);

    while (elf_load_read_available(self))
      boot_tx_write8(elf_load_read8(self));
  }
  while (PT_ISRUNNING(state));

  return state;
}

The listing leaves out the ? option. One thing in the bootloader does not go through the library: opening the port. uart0_open() works out its divisor at run time with 32-bit divisions, which cost 292 bytes, and enables the receive interrupt; uart0_close() ends with sei(). A bootloader knows its baud rate when it is built, polls, and must not enable interrupts, so it sets the four registers itself and clears UCSR0B before it starts the image. Both are in section 7 (findings 2, 7 and 20).

Limits. XMODEM cannot tell the sender to stop early. Sending a stripped file removes the wasted time; a sender that stops after the last loadable byte would do the same for any file. In simulation at 115200 baud a block took 13.7 ms: 0.23 s for example 12 stripped, 3.18 s with its debug information. measured

The watchdog and the reset cause

BOOT_RESET_CAUSE = MCUSR;           /* GPIOR0: where the image reads why the part was reset */
MCUSR = 0;                          /* WDRF has to go before the watchdog can be changed    */
BOOT_WDT = _BV(WDCE) | _BV(WDE);    /* the timed sequence ...                               */
BOOT_WDT = _BV(WDP3) | _BV(WDP0);   /* ... off; where a fuse keeps it on, 8 s               */

These statements run as soon as the stack is set, and the scheduling loop executes WDR on every idle pass for a part whose fuses keep the watchdog running: 22 bytes together. The image starts with the watchdog off, MCUSR at zero and the cause in GPIOR0; in the tests it read 01 after power-on and 08 after a watchdog reset. measured

Optiboot uses the watchdog for four things. read

  1. As its only timer. Its receive routine is a loop that waits for a byte and has no timeout. The watchdog, armed at one second and reset with every good byte, is the timeout, and it costs one instruction.
  2. As its way out. It does not jump to the application. It lets the watchdog reset the part, sees the cause on the way back in, and starts the application before it has touched a register. The application finds the part as a reset leaves it.
  3. To decide whether to run at all. Only a reset through the pin makes it wait. After power-on, a brown-out or a watchdog reset the application starts at once.
  4. Because it has to. The cause must be cleared and the watchdog switched off, or the part is reset every 16 ms.

This bootloader takes the last two. The fourth is not a choice: it is the 22 bytes above, on in every build. The third is BOOT_CONF_WINDOW_AFTER, 20 bytes, with Optiboot's rule as the default: wait only after a reset through the pin. The first does not fit the protocol. XMODEM is driven by the receiver: after a silence the receiver has to send its probe or its negative acknowledgement again, so it needs a clock that ticks without resetting the part, and a reset in the middle of a transfer would throw away a session that a negative acknowledgement recovers today. That clock is the idle count of the scheduling loop. The second is reached another way. What a reset would restore and the bootloader has changed is four UART registers, so it writes their reset values back before it jumps, 12 bytes (BOOT_CONF_UART_RESET). The image then finds the part as a reset leaves it, with three stated differences: the watchdog is off, MCUSR is zero, and GPIOR0 holds the cause.

6.6Parts without a boot section proposed

On a classic ATtiny, reset always goes to address 0, and nothing protects the loader's pages. The loader sits at the top of flash and makes four provisions.

  1. The reset vector is redirected. When page 0 of an image passes through the page cache, the loader keeps the image's own start address for the record and replaces the first instruction with a jump to itself. The other vectors stay the image's; the loader uses no interrupts.
  2. Erase runs from the top down, page 0 last. Before the first page is written, all application pages are erased starting just below the loader. While page 0 still holds the old redirected vector, a reset reaches the loader through it. Once page 0 is erased, everything below the loader is erased, and erased flash executes as a harmless skip instruction until the program counter runs into the loader. This closes the window urboot's documentation warns about.
  3. A landing pad. Because that skip instruction may skip one word, the loader starts with a one-word no-op.
  4. Its own serial port. The ATtiny85 has no USART. boot/softuart.h provides the polled part of uart0 on two pins, under the same names, so the bootloader source is the same on every part.

The loader's own pages remain unprotected against a runaway application. On these parts the design is an updater, not a guaranteed recovery path, and an ISP programmer remains the last resort.

The ATtiny85 build (1,958 bytes, 313 bytes of RAM, with BOOT_CONF_VIRTUAL_RESET and BOOT_CONF_SOFT_UART) compiles and has not executed. Points 2 and 3 were checked on the ATmega328P in simavr, which executes an erased word as the same skip instruction a real AVR does. Started in erased flash below the loader, at either word alignment and with the skip taken or not, execution arrived in the loader all four times. In a control build without the landing pad, one of the four cases skipped the loader's first instruction and ran its rule table as code. measured

    && bootrom_version() == BOOTROM_VERSION
    && bootrom_has_load_thread()
    && bootrom_load_size() <= sizeof(loader_workspace);

What is shared. The system and the bootloader are built separately, so they agree on the head of struct elf_load only: the protothread state, the mailbox, the window, the result, the entry point and the key of 6.8. Those fields have the same layout in every build for one part. Everything behind them is private to whoever runs the thread, and the table says how much room that takes. The system brings a workspace at least that large; the loader process adds a margin of 16 bytes to its own sizeof for a bootloader that was built with more options.

Rules. Code reached through the table uses the caller's memory and stack only. flash_page_write() switches interrupts off while it works, because the caller's interrupt handlers live in the section being programmed, and restores the caller's interrupt state on return. The thread itself runs with the caller's interrupts enabled and calls nothing outside the boot section.

Why addresses and not jumps. The first version of the table held relative jumps. In an 8 KB boot section a relative jump at the end of flash cannot reach a function near the start of the section, and the link failed; and link-time relaxation is free to shorten a long jump and shift whatever follows it. Plain addresses have neither problem.

Above 128 KB. The two services are called through the header and never fetched as pointers, because a pointer cannot hold their address everywhere. On an ATmega2560 a function pointer has 16 bits and reaches the first 128 KB, and the 4 KB boot section lies at 0x3F000. The first version called through a truncated pointer; on the simulated part the call ended up in the wrong place and the page stayed unwritten. measured The usual answer is to set EIND around an indirect call. That is wrong here: the load thread runs with interrupts enabled, and protoduino's UART handlers call their callbacks through pointers, so a handler that fires while EIND is set would jump into the wrong half of flash. The header therefore does it without EIND:

; ptstate_t bootrom_far_load_thread(struct elf_load *self, uint32_t word_address)
;   self is in r24-r25 where the thread expects it; the address arrives in r20-r23
push r20          ; the address goes on the stack as a return address ...
push r21
push r22
ret               ; ... and RET takes all three bytes of it

The service then returns straight to whoever called the routine. The address is the last argument, so the arguments of the service are already in the registers it expects them in, and the routine for flash_page_write() is the same four instructions with other registers. Both are written at file level and only declared to the compiler: as a C function without a body the first attempt was taken for a function that never returns, and the code after the call was dropped. On parts up to 128 KB the header makes a plain indirect call. The bootloader itself contains one indirect jump, the IJMP into the image, which clears the upper address bits by definition.

Cost and evidence. On the ATmega328P the page service adds 12 bytes to the bootloader and the thread another 76: the table, the lower bound of the window and the check of the key. In the previous draft the blocking session cost 396 bytes to export, because it had to exist twice. An application installed through the bootloader programmed a page through the table and read it back, on the ATmega328P (T10) and on the ATmega2560 for a page below and one above 64 KB (T20, T21). A kernel had modules loaded through both entries on the ATmega328P (M1, M3, M9) and on the ATmega2560 (M10, M11). measured One limit applies: simavr does not enforce the rule that SPM must run from the boot section (S2 in 8.1), so these runs show the calling convention and not the hardware permission.

6.8Modules

A module is an executable linked into a flash slot. Its first bytes are a descriptor, and the ELF entry point is the descriptor's address.

typedef struct module {
  uint16_t              magic;      /* MODULE_MAGIC, 'p' 'M'                                   */
  uint8_t               abi;        /* MODULE_ABI                                              */
  uint8_t               flags;      /* reserved, 0                                             */
  uint16_t              kernel_id;  /* kernel build the module is linked for: the key          */
  const process_type_t *type;       /* the process type the module adds                        */
} module_t;

Anatomy of a module

This is the module of the tests, complete (prototype/kernel/count_module.c). It keeps a counter in its process struct, writes to the serial device process of the kernel through a pipe, and takes turns through the scheduler of the kernel. Nothing in it says that it is loaded later, except the last line.

The loader process

src/mod/loader.h is a process type in a header, like the modules beside it. loader_start(slot, line) starts it and connects it to a device in both directions with process_connect(); when it ends it gives the input of that device back to whoever read it before, so a shell can start it on its own line. Its thread, shortened by the comments:

  PROCESS_BEGIN();

  if (!loader_has_thread() || !flash_is_writable())  /* the bootloader's, or the kernel's own copy */
    LOADER_RAISE(ERR_INIT_NOSUP);
  if (self->slot >= MODULE_CONF_SLOTS || module_is_installed(self->slot))
    LOADER_RAISE(ERR_STATE_LOCKED);

  if (!pt_process->has_pipein || !pt_process->has_pipeout)    /* started without a line */
    LOADER_RAISE(ERR_PIPE_BROKEN);

  elf_load_init(load,
                MODULE_SLOT_ADDR(self->slot),
                MODULE_SLOT_ADDR(self->slot) + MODULE_CONF_SLOT_SIZE,
                ELF_LOAD_MODULE,
                LOADER_CONF_PATIENCE);
  load->key = module_kernel_id();
  timer_set(&self->silence, clock_from_seconds(1));

  do {
    if (!elf_load_write_available(load)) {
    } else if (ipc_pipe_available(PROCESS_PIPEIN()) > 0) {
      ipc_pipe_read(PROCESS_PIPEIN(), &self->byte, 1);           /* the next byte from the sender */
      elf_load_write8(load, self->byte);
      timer_restart(&self->silence);
    } else if (timer_expired(&self->silence)) {
      elf_load_timeout(load);                                    /* or the news that there is none */
      timer_restart(&self->silence);
    }

    self->state = (uint8_t)loader_thread(load);

    while (elf_load_read_available(load) > 0) {                  /* its replies go out */
      self->byte = elf_load_read8(load);
      PROCESS_PIPE_WRITE(&self->byte, 1);
    }

    if (PT_ISRUNNING(self->state) && ipc_pipe_available(PROCESS_PIPEIN()) == 0) {
      if (!self->ticking)                                        /* everybody else runs */
        self->ticking = process_post(pt_process, EVENT_INTERVAL, (process_data_t)pt_process);
      PROCESS_WAIT_EVENT();
    }
  } while (PT_ISRUNNING(self->state));

When the thread has stopped, the loader looks at how it ended, turns the file in the slot into a running process, and cleans up after itself:

  if (self->state == PT_EXITED)
    LOADER_RAISE(ERR_CONN_TIMEOUT);
  if (self->state != PT_ENDED)
    LOADER_RAISE(self->state);

  self->state = module_check(self->slot);         /* the file is in the slot: is it a module for us? */
  if (self->state != ERR_SUCCESS)
    LOADER_RAISE(self->state);

  module_table_write(self->slot, true, loader_workspace.bytes);
  if (self->notify != NULL)
    process_post(self->notify, EVENT_MODULE_INIT, module_start(self->slot));
  else
    module_start(self->slot);
  process_post(pt_process, PROCESS_EVENT_EXIT, NULL);   /* brings us back for PT_FINALLY */

  PT_CATCHANY(&pt_process->pt)
  {
    self->state = (uint8_t)PT_ERROR_STATE;          /* the scheduler passes it to the error logger */
    process_post(pt_process, PROCESS_EVENT_EXIT, NULL);
    PT_THROW(&pt_process->pt, self->state);
  }

  PT_FINALLY(&pt_process->pt)
  {
    if (self->line != NULL && self->previous != NULL)   /* give the line back */
      process_connect(self->line, self->previous);
  }

  PROCESS_END();

The loader is an ordinary citizen. It reads PROCESS_PIPEIN(), writes with PROCESS_PIPE_WRITE(), keeps time with sys/timer.h, reports success with EVENT_MODULE_INIT and failure by ending with an error, which process.c hands to the error logger like the error of any process. Three lines in it work around the scheduler as it is today: the event it posts to itself before it ends, the single ticking event, and the poll inside LOADER_RAISE() (7, findings 14, 15 and 21).

The ticking event carries the process as its data. The first version posted it without, and worked until the kernel got a tick (sys/tick.h), which posts the same event number to every process: the loader took each tick for its own event and posted another, the queue filled within eight ticks, and from then on nobody could post, the loader's own report included. A process that posts an event to itself has to be able to tell it from everybody else's. measured

What a kernel offers. A module can only call what the kernel contains, and a build contains what somebody in it refers to. With link-time optimisation, which the Arduino IDE uses, that is stricter still: a function the kernel calls in one way only may survive in a form shaped for that call. sys/module.h therefore keeps a table that refers to the functions a module is likely to need (events, polls, process_new(), process_connect(), the pipe functions, micros()), and a sketch adds its own with MODULE_CONF_API. A second record holds where the slots are, so that the host tool reads slot addresses, part and clock from the kernel file and asks for nothing. A module that calls something the kernel does not offer fails at link time with the name of the function. measured

The identity is a CRC-16 that module_init() computes over the kernel's own flash image; the host computes the same value from the kernel's ELF file and passes it to the module's link. It does not come from the bootloader's image record, because Optiboot keeps none.

Checked before the first write. The kernel hands its identity to the load thread as self->key. In ELF_LOAD_MODULE mode the sink compares the two bytes that arrive for offset 4 of the window, where a descriptor carries kernel_id, and refuses the file with ERR_INIT_DEPENDENCY. Those bytes are in the first page, which is still in the cache at that moment, so a module for another kernel build changes nothing (M5: 0 bytes programmed). The previous draft could only refuse such a module after it had overwritten the slot. measured

Slots, the module table and the life cycle

  • Slots. MODULE_CONF_SLOTS ranges of MODULE_CONF_SLOT_SIZE bytes from MODULE_CONF_BASE, above the kernel image and below the image record. The tests use two slots of 2 KB at 0x6000. A module is linked for one slot; with 4.8, any.
  • The module table. One page behind the last slot: a magic and, per slot, the identity of the kernel its module belongs to. It is written after the module has been loaded and checked, so a load that was cut short leaves nothing that could be started.
  • Load. The thread programs the module's pages into the slot. The loader process then calls module_check(), module_table_write() and module_start(), which is process_new() with the type from the descriptor and RAM from the slot's block.
  • Start-up. module_autostart() starts every slot whose table entry names this kernel. No loader is involved, which is all that level 1 needs.
  • Remove. module_table_write(slot, false, ...) and process_destroy(): the shell's del. The flash of the slot is left as it is; a new module is accepted once the process of the old one has ended. measured

On Optiboot

A developer who prefers Optiboot keeps it. The firmware is uploaded the usual way, and the protoduino kernel loads modules itself, with LOADER_CONF_THREAD set to LOADER_THREAD_OWN in the sketch. The flash driver finds Optiboot by itself. What Optiboot offers was read from its source (version 8.3): the second word of the bootloader is a jump to do_spm(address, command, data), which performs one SPM step and re-enables the read-while-write section after an erase or a write; a build without the feature has a ret there instead. flash_is_writable() recognises a usable Optiboot by a major version from 8 up to 127 in the last byte of flash, which erased flash is not, and a jump in that second word. What the tests are and are not

The kernel in M1 to M12 is prototype/kernel/kernel.c: a sketch with setup() and loop() on process.c, ipc.c, the serial device process, the serial layer and the UART driver of the library, built without the Arduino core. A stand-in of 40 lines supplies main(), timer 0 and micros(). Its kernel process doubles as the error logger of the scheduler, which is how it learns that a load failed.

The kernel in S3 and S4 (9.2) is a sketch of the examples, 42-shell-loader: a shell, two modules and two slots. Built with the Arduino builder against the Arduino core, and with avr-gcc alone, it was uploaded through the bootloader inside protosim and took modules over its command line. Still open:

  • Hardware.
  • The ATmega1284P kernel, which was not built.
  • A second serial device as the line of the loader. The loader no longer names one, but only serial_process0 was used.

Rules and hazards

  • No static variables. No interrupt handlers: the vector table belongs to the kernel.
  • The slots and the module table lie in the first 64 KB of flash, also on a larger part: the scheduler reads a process type and its name with a 16-bit address and calls the thread through a 16-bit pointer. A configuration that puts them higher is a build error.
  • A process struct is at most 255 bytes, because process_type_t.size is one byte, and at most MODULE_CONF_RAM_SIZE.
  • A callback a module registers with the kernel, such as a UART receive handler, points into the module. It must be removed in the module's PT_FINALLY block. The kernel cannot check this.
  • On a chip, programming a page stops everything for 7.4 to 9.0 ms with interrupts off: the datasheet gives 3.7 to 4.5 ms each for the erase and the write. One timer 0 overflow per millisecond is lost in that time, so micros() falls behind by that much per page.
  • While a block is on the wire, events wait behind the polls of the serial device (7, finding 14).
  • The reserved byte of the descriptor is where a signature over the module would be announced. It is reserved, not designed.

RAM. What the protothread costs. The blocking bootloader of the previous draft was 1,640 bytes; the protothread one was 2,014, and after the assembly and the numbered continuation points described below it was 1,938. What would shrink it. Nothing has been tried from this list, in order of expected yield:

  1. A hand-written per-byte path for the stream and the frame check. It would live beside the C version, which the host build needs: a last resort.
  2. Replace the 128-byte block with a smaller frame, which also suits the small ATtinys.
  3. Build with a newer avr-gcc. The repository's platformio.ini already points at one; only 7.3.0 was available here.

What already mattered, in the order it was found. The first version of the protothread bootloader was 2,520 bytes. One wait point in the thread with a plain function that judges a frame, a mailbox the thread never has to wait on, and setting the UART registers directly (286 of the bytes) brought it to 2,094. -fno-move-loop-invariants -fno-ivopts -fno-tree-scev-cprop saved 26. A workspace that needs no clearing, and with it no .bss code, saved 48. The assembly described next saved 62, and numbered continuation points 14. -mstrict-X keeps the workspace pointer out of the X register. measured

Numbered continuation points. lc-switch.h identifies a wait point by the source line it stands on, so the number is stored and compared as 16 bits as soon as the line is above 255. That made the size of the thread depend on where it stands in its file: six comment lines added above it moved one wait point past line 255, and the bootloader grew by two bytes. src/sys/lc-counter.h is the same header with the points numbered 1, 2, 3 from the compiler's __COUNTER__; the bootloader selects it through LC_INCLUDE, which lc.h already provides for. What Optiboot does in assembly. Optiboot 8.3 is one C file of 1,689 lines, and its ATmega328 image is 474 bytes. It is C almost throughout: ten inline-assembly statements and a header that re-issues avr-libc's SPM sequences with OUT. Its size comes less from assembly than from what it leaves out: no file format, no checksum, no record of what is installed; the host decides and the device stores pages. It uses assembly where the compiler cannot say a thing at all or says it badly. read

What was taken from it. Erasing and programming a page was 130 bytes from the compiler; with OUT to the control register and one routine that issues every SPM and waits, it is 76, and those 54 bytes put segment merging back into the 2 KB section of the ATmega328P. IJMP into the image, in place of an indirect call followed by a loop that is never reached, saved 8. The assembly is confined to src/cpu/avr/flash.c and one line of boot/boot.c: the stream stays in C because it also builds on the host, the load thread because it is the part that should read like protoduino. Optiboot's -fno-split-wide-types changed nothing. measured

Time. Line time dominates: in simulation a block took 13.7 ms at 115200 baud on the ATmega328P, 15.1 ms on the ATmega2560 and 14.0 ms through the loader process, about 9 KB per second. A chip adds the time to program each page (S5 in 8.1).
