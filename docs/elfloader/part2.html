5.3Start-up behaviour

After reset the loader probes for a sender: it transmits C, waits about a second, and repeats. A transfer may begin at any probe. If none begins within the configured number of probes and the image record is intact, the image is started. If the record is not intact, the loader probes for ever. In the prototype the window is always applied and comes to about five seconds with three probes measured. That is too long for a product, so the entry condition is a configuration choice: always wait; wait only after an external reset; or wait only when the application asked or no valid image exists. proposed

5.5Limits

  • At most 255 program headers; at most ELFLD_CONF_MAX_SEGMENTS separate loadable segments after adjacent ones are merged. Plain firmware needs one.
  • File offsets and sizes must fit the build's address width: 64 KB on small parts, 16 MB on large ones.
  • Flash segments must arrive in ascending address order, because the page cache only moves forward. avr-gcc output does. A read-modify-write option would lift this. proposed
  • The serial path needs 128 bytes of RAM for an XMODEM block and one flash page more.

6.2The core

/* Start a load. Flash bytes outside [lo, hi) are refused before anything is written. */
void    elfld_begin(elfld_t *c, elfld_addr_t lo, elfld_addr_t hi);

/* Push the next n bytes of the file. Returns ELFLD_MORE, ELFLD_DONE or an ELFLD_E_* code;
   after DONE or an error the rest of the file is ignored. */
uint8_t elfld_write(elfld_t *c, const uint8_t *p, uint8_t n);

/* Supplied by the port: store one byte. Return 0 to continue. */
uint8_t elfld_sink(uint8_t space, elfld_addr_t addr, uint8_t byte);

Header rules. Seventeen bytes of the ELF header must each have one exact value: the magic, the class, the byte order, the file type, the machine, the position and size of the program headers. They are checked by a loop over a 34-byte table of offset and value pairs, which is smaller than seventeen comparisons and easy to extend.

What is remembered. The data of a segment arrives after all the headers, so each loadable segment is remembered as three numbers: the count of file bytes to skip before it, the address of its next byte, and the bytes still to deliver. Storing the gap and not the absolute offset removes the need to count file position at all. A segment that continues the previous one, both in the file and in memory, is merged into it. .text and .data always do, so plain firmware is one remembered segment.

Context layout. The scratch area for header bytes is the first member of the context, so that header bytes and the hot control fields are all within the 63-byte reach of one pointer. On AVR that matters more than it looks: see 6.10.

What building the prototype taught

  • A refused file must not cost the installed image. The first version erased the record when the first block arrived. A wrong file then left a working board without a valid image. Invalidation now happens with the first page write, after the headers are accepted. Test T7 guards it.
  • Above 64 KB, tables in flash need the far read. In the ATmega2560's boot section the rule table sits beyond the reach of LPM. The loader refused every file until the table was read through ELPM.
  • Service code owns no RAM. When the application calls into the boot section, the loader's variables are the application's memory. The first service copied into the loader's page buffer and would have corrupted the caller. It now works on the caller's buffer alone.
  • Do not pin registers. An attempt to force the context pointer into the Y register with a local register variable compiled, did nothing on one part and miscompiled on the other. The supported way is the compiler option in 6.10.

6.3Flash back-end

The sink for flash is a cache of one page. A byte for a different page first commits the cached one: erase, fill the chip's page buffer, write, re-enable the read-while-write section. The cache starts as all 0xFF, so a partly covered page is padded. The back-end is the only part that differs between chip families:

Back-endPartsNotesStatus
SPM from a boot sectionmegaAVRRead-while-write must be re-enabled before the application section is read againmeasured
SPM from anywhereclassic tinyAVRThe CPU halts during a write; needs the SELFPRGEN fuse; reset vector handling in 6.6built
NVMCTRLtinyAVR 0/1/2, AVR DxDifferent mechanism; not designed here–

The lock bits must leave SPM writes to the application section enabled, or no bootloader of any kind can work.

6.4Transport: XMODEM-CRC

The bootloader speaks XMODEM with 16-bit CRC. It is decades old and exactly right for this job.

PropertyWhy it matters here
Built into terminal programs on every platformThe unmodified .elf can be sent with no tool of ours installed.
The receiver sets the pace: one block, one acknowledgementThe loader programs pages while handling a block and acknowledges afterwards. No flow-control lines and no receive buffer are needed with a polled serial port.
Blocks are numberedA block repeated after a lost acknowledgement is recognised and not applied twice.
CRC-16 per blockThe same CRC routine also protects the image record and the image, so there is one checksum routine in the loader.

A block is SOH, the block number, its complement, 128 data bytes and two CRC bytes. The loader holds a block in RAM until its CRC has passed, and only then feeds it to the core, so damaged bytes never reach flash. One extension is used: after cancelling with two CAN bytes the loader sends the reason code. Terminal programs ignore it; the pd tool prints it.

The limits are the 128 bytes of RAM a block needs, and that XMODEM cannot tell the sender to stop early. Sending a stripped file, or using the pd tool, which stops after the last loadable byte, removes the wasted time. In simulation at 115200 baud a block took 13.3 ms of line time: 0.22 s for example 12 stripped, 3.06 s with its debug information. measured

The runtime loader (cut C) uses the same framing over a protoduino pipe from the serial process. Stop-and-wait is not optional there: programming a page keeps interrupts off for several milliseconds, and a sender that kept transmitting would overrun the receiver.

An erased page fails both the magic and the CRC, so “no record” needs no flag. The record after test T1 read 70 44 00 00 80 01 00 13 80 c1 aa: entry 0, image end 0x000180, image CRC 0x8013. That 16-bit value doubles as the identity of the firmware build for modules (6.8). The rest of the record page is reserved for module records.

6.6Parts without a boot section proposed

On a classic ATtiny, reset always goes to address 0, and nothing protects the loader's pages. The loader sits at the top of flash and makes four provisions.

  1. The reset vector is redirected. When page 0 of an image passes through the page cache, the loader keeps the image's own start address for the record and replaces the first instruction with a jump to itself. The other vectors stay the image's; the loader uses no interrupts.
  2. Erase runs from the top down, page 0 last. Before the first page is written, all application pages are erased starting just below the loader. While page 0 still holds the old redirected vector, a reset reaches the loader through it. Once page 0 is erased, everything below the loader is erased, and erased flash executes as a harmless skip instruction until the program counter runs into the loader. This closes the window urboot's documentation warns about.
  3. A landing pad. Because that skip instruction may skip one word, the loader starts with a one-word no-op.
  4. Its own serial port. The ATtiny85 has no USART; the build uses a bit-banged port.

The loader's own pages remain unprotected against a runaway application. On these parts the design is an updater, not a guaranteed recovery path, and an ISP programmer remains the last resort. This path compiles and has not executed. The simulator cannot settle point 2: simavr treats 0xFFFF as an invalid opcode.

6.7The service entry

/* last four bytes of flash:  rjmp bootsvc_write_page ; 'p' ; 'D' */
typedef void (*pd_write_page_fn)(uint32_t addr, const uint8_t *page);

if (pgm_read_byte(FLASHEND - 1) == 'p' && pgm_read_byte(FLASHEND) == 'D')
  ((pd_write_page_fn)((FLASHEND - 3) / 2))(0x6000UL, page);     /* returns when the page is programmed */

The entry disables interrupts while it works, because the caller's interrupt handlers live in the section being programmed, and restores the caller's interrupt state on return. It costs 28 bytes in the loader. In simulation an application installed through the loader called it and read its page back correctly measured. Two limits apply to that result: simavr does not enforce the rule that SPM must run from the boot section, so the test shows the calling convention and not the hardware permission; and on parts above 128 KB the entry lies beyond a 16-bit function pointer and needs a small far-call trampoline, which is not built.

The planned form is a short table, not a single entry: write a page, begin a load, feed a load, report information. With the core exported this way, the kernel's module loader carries no second copy of it. proposed

6.8Modules proposed

A module is an executable linked into a flash slot. Its first bytes are a descriptor, and the ELF entry point is the descriptor's address, so the standard header field tells the loader what was installed.

#include <protoduino.h>
#include <sys/process.h>
#include <sys/elf/module.h>

PROCESS_DEFINE(blink, "blink", 2,
  uint8_t  pin;                  /* all state lives in the process struct */
  uint16_t ticks;
);
PD_MODULE(blink);                /* descriptor: magic, ABI, firmware id, &process_type_blink */

PROCESS_THREAD(blink, ev, data)
{
  blink_t *self = PROCESS_SELF(blink);
  PROCESS_BEGIN();
  /* ... ordinary protoduino process code, calling kernel functions directly ... */
  PROCESS_END();
}
# the kernel's functions, as addresses the module may link against
avr-nm firmware.elf | pd abi > kernel-abi.ld          # PROVIDE(process_post = 0x00001a2c); ...

avr-gcc -Os -mmcu=atmega328p -nostartfiles -nostdlib \
        -Wl,-T,pd-module.ld -Wl,-T,kernel-abi.ld \
        -Wl,-e,pd_module -Wl,--defsym=__pd_kernel_id=0x8013 \
        -o blink.elf blink.c

A reduced form of this recipe was linked and loaded on the host measured. The result is an 848-byte file with one flash segment at the slot address, its entry point on the descriptor, and calls into the kernel as plain absolute call instructions. The core accepted it when the window was the slot it was linked for, and refused it with RANGE for a different slot; the firmware image offered to a module slot was refused the same way. The module linker script turns static variables into a link error: module has static variables: keep state in the process struct.

Slots, records and life cycle

  • Slots. Pages between the end of the firmware image and the record page. The information reply names the next free slot, so the host can link for it. With 4.7, any slot.
  • Records. A few bytes per module in the record page: state, first page, page count, descriptor address, CRC.
  • Install. The descriptor is the first thing in the first segment, so the loader can check its magic and firmware id while the first page is still in RAM, before any write. Pages go through the service. The record is written last. Then process_new() with memory from a module pool, and process_start().
  • Start-up. For every intact record whose firmware id matches, start the process again.
  • Remove. process_destroy(), which delivers the exit event, then clear the record.

Rules and hazards

  • No static variables. No interrupt handlers: the vector table belongs to the kernel.
  • A process struct is at most 255 bytes, because process_type_t.size is one byte.
  • A callback a module registers with the kernel, such as a UART receive handler, points into the module. It must be removed in the module's exit handler. The kernel cannot check this.
  • While a page is programmed, interrupts are off for milliseconds. Installing a module disturbs time-critical processes.
  • A signature over the module, checked before the record is written, would fit in the descriptor. It is reserved, not designed.

6.9Compile-time configuration

Configuration follows the pattern protoduino already uses in its *.conf.h files: every setting has a default and can be overridden. Three rules apply. Derive from the part wherever possible: address width from FLASHEND, expected core family from __AVR_ARCH__, page size from SPM_PAGESIZE. A feature that is off costs nothing. And fail the build, not the device: a missing setting is an #error, and a loader that outgrows its boot section must fail at link time.

What fits where. The ATmega328P offers boot sections of 0.5, 1, 2 and 4 KB. Every 328P build fits the 2 KB section, with 104 bytes to spare when everything is on. None fits 1 KB: the default is about 650 bytes over. The ATmega2560 offers 1, 2, 4 and 8 KB; the default build is 120 bytes over the 2 KB section and so needs 4 KB today. RAM on the 328P is the XMODEM block (128), the page buffer (128), the core context (84) and nine bytes of flags.

Why it is this big, and what would shrink it. The code is ordinary C and the cost is spread evenly: ten to thirty bytes per source line, mostly 16-bit arithmetic on fields reached through a pointer. Nothing has been tried from this list, in order of expected yield:

  1. Write the per-byte path and the SPM sequences in assembly, as Optiboot and urboot do.
  2. Replace the 128-byte block with a smaller frame, which also removes the buffer-then-apply loop and suits the small ATtinys.
  3. Build with a newer avr-gcc. The repository's platformio.ini already points at one; only 7.3.0 was available here.
  4. Take the minimum cut: without merging, the family check and the image CRC the loader is 100 bytes smaller.

One compiler option already mattered. By default avr-gcc kept the context pointer in the X register, which has no displacement addressing, and spent three instructions on each field access. With -mstrict-X the header check alone fell from 154 to 120 bytes. measured

Time. Line time dominates: 13.3 ms per block at 115200 baud in simulation, about 9.6 KB per second. Real hardware adds the time to erase and program each page, a few milliseconds each, which simavr does not model.
